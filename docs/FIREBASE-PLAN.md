# Таблица лидеров, вход и облачный прогресс на Firebase — план внедрения

в [FIREBASE-SETUP.md](FIREBASE-SETUP.md).

## Цель и рамки

- Игрок регистрируется и входит по логину и паролю, без email и сторонних аккаунтов. Логин
  может быть на кириллице или латинице и показывается в таблицах как имя игрока.
- Таблицы лидеров: лучшие забеги по времени, убийствам и кодам, победы и «Продакшен», а также
  накопленные итоги — убийства, коды, число игр. Каждая таблица есть общая и по каждой карте.
- У игрока есть экран «Моя статистика» с теми же показателями.
- Прогресс (`utreys-progression-v1`: коды, герои, улучшения, достижения, рекорды) хранится в
  Firestore и переносится между устройствами.
- Без входа, без сети и без настроенного Firebase игра работает как сейчас: `localStorage`
  остаётся основным хранилищем, облако — синхронизируемая копия.

**Вне плана:** восстановление пароля по почте (почты нет), серверная проверка результатов
(нужны Cloud Functions и тариф Blaze), друзья, сезоны, чат. Сохранение текущего забега
(`utreys-run-v1`), журнал забегов и настройки остаются локальными.

## Решения

| Вопрос       | Решение                                                                                    | Почему                                                                                             |
| ------------ | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| Способ входа | Firebase Auth, провайдер Email/Password; логин кодируется в служебный адрес                | Готовые хэширование паролей, сессии и защита от перебора; игрок email не вводит и не видит         |
| Логин        | 3–16 символов: кириллица или латиница (не вперемешку), цифры, `_`, `-`; без учёта регистра | Смешение алфавитов запрещено, чтобы «Вася» на латинской «а» не выдавал себя за другого             |
| Пароль       | От 6 символов (минимум Firebase), поле «повторите пароль» при регистрации                  | Просто для игрока                                                                                  |
| Статистика   | Один документ `stats/{uid}` на игрока со всеми показателями, общими и по картам            | Одна запись за забег; таблицы строятся по вложенным полям без составных индексов                   |
| База         | Cloud Firestore, SDK `firebase/firestore/lite`                                             | Lite — без офлайн-кэша и подписок, в 2–3 раза меньше; офлайн у нас и так есть через `localStorage` |
| Загрузка SDK | Динамический `import()` после первого кадра меню                                           | Firebase не увеличивает время старта игры                                                          |
| Включение    | Только если заданы `VITE_FIREBASE_*`                                                       | Тесты, smoke и форки собираются без Firebase                                                       |
| Античит      | Правила Firestore: владелец, диапазоны, только рост итогов и рекордов; позже App Check     | Игра целиком клиентская, полную защиту даёт только сервер                                          |

## Логин и пароль

**Ключ логина.** Из логина получается ключ: `NFC`, нижний регистр, `ё → е`. Так «Алёна»,
«алена» и «АЛЕНА» — один и тот же логин. Отображается логин так, как его ввели при
регистрации.

**Служебный адрес.** Firebase Auth входит только по адресу и паролю, а кириллицу в адресе
он не гарантирует. Поэтому адрес — `hex(UTF-8(ключ)) + '@' + LOGIN_DOMAIN`, где
`LOGIN_DOMAIN` — `<projectId>.firebaseapp.com`. 16 кириллических символов дают 64 hex-символа —
ровно предел имени в адресе. Письма не отправляются, подтверждение адреса не используется.

**Регистрация:**

1. Проверка формата логина и пароля на клиенте.
2. `createUserWithEmailAndPassword`; `auth/email-already-in-use` → «Логин занят».
3. Транзакцией создаются `logins/{ключ}` (`uid`) и `users/{uid}` (`login`, `loginKey`). Если
   транзакция не прошла, только что созданный аккаунт удаляется (`deleteUser`), игрок видит
   ошибку и может повторить.

**Вход** — `signInWithEmailAndPassword`; `auth/invalid-credential` → «Неверный логин или
пароль», `auth/too-many-requests` → «Слишком много попыток, подождите». Сессия хранится в
браузере (`browserLocalPersistence`). Смена пароля в игре — `updatePassword` после повторного
ввода старого.

**Забытый пароль:** игрок пишет владельцу, владелец задаёт новый пароль скриптом
`tools/reset-password.cjs` (Firebase Admin SDK, ключ сервисного аккаунта хранится вне
репозитория). В консоли Firebase пароль напрямую не задаётся. Инструкция — в
FIREBASE-SETUP.md.

## Статистика и таблицы лидеров

### Показатели

Каждый показатель считается в разрезе «все карты» и по каждой карте из `data/maps/maps.js`
(сейчас `empty` и `serverRoom`; новая карта появляется в таблицах автоматически).

| Показатель           | Поле             | Сортировка | Что значит                                                              |
| -------------------- | ---------------- | ---------- | ----------------------------------------------------------------------- |
| Лучшее время         | `bestTime`       | убыв.      | самый долгий забег, секунды                                             |
| Больше всего убийств | `bestKills`      | убыв.      | убийства в одном забеге                                                 |
| Больше всего кодов   | `bestCodes`      | убыв.      | коды, полученные за один забег (`s.earned`, с бонусами конца)           |
| Победа               | `victoryScore`   | убыв.      | `load × 100000 − время в десятых секунды`: выше нагрузка, затем быстрее |
| Продакшен            | `productionTime` | убыв.      | самое долгое время в «Продакшене»                                       |
| Всего убийств        | `totalKills`     | убыв.      | сумма за все забеги                                                     |
| Всего кодов          | `totalCodes`     | убыв.      | все полученные коды (не текущий баланс)                                 |
| Всего игр            | `games`          | убыв.      | число забегов                                                           |

Вместе с рекордом хранится, каким героем и на какой нагрузке он поставлен (`bestTimeHero`,
`bestKillsHero` и т. д.), чтобы показать это в строке таблицы.

### Что считается забегом

- Забег засчитывается при первом завершении: победа, смерть, выход в меню или перезапуск
  (`countRun` в `game-flow.js` вызывается из `finish`, `menu` и `start`). Забеги короче
  10 секунд не считаются, чтобы «старт → выход» не накручивал число игр.
- Если после победы забег продолжается в «Продакшене», при следующем завершении в итоги
  добавляется только прирост убийств и кодов, а `games` не растёт.
- Отправка — в конце `finish` (`src/app/game-flow.js`), после начисления бонусов за
  нагрузку и «Жадность», чтобы `s.earned` был окончательным.
- Забеги, сыгранные без входа, в таблицы не попадают. Забеги без сети ставятся в очередь в
  `localStorage` и отправляются, когда сеть появится.
- Итоги в таблицах начинаются с нуля с момента регистрации: старые локальные счётчики не
  переносятся, их нельзя проверить.

### Экраны

- **«Лидеры»** в главном меню, смотреть можно без входа. Сверху — вкладки «Рекорды забега» и
  «Итоги»; внутри — показатель и карта («Все карты», «Дата-центр Utrace», «Серверный зал»). Топ-50:
  место, логин, значение, герой и нагрузка для рекордов. Внизу — своя строка с местом, если
  игрок не в топе (место = `getCount` по записям с большим значением + 1).
- **«Моя статистика»** в панели аккаунта: все показатели таблицей «показатель × карта» и место
  в каждой таблице. Без входа показывается локальная статистика с этого устройства.
- **Итоги забега:** «Новый рекорд: лучшее время, 12-е место» для каждого улучшенного
  рекорда. Без входа — кнопка «Войти, чтобы попасть в таблицу»; после входа этот забег
  отправляется.
- Таблица кэшируется на 60 с, чтобы переключение вкладок не тратило квоту чтений.

### Локальная статистика

В `persistence.js` добавляется `mapStats`: те же показатели по картам. Она нужна для экрана
«Моя статистика» без входа и синхронизируется вместе с прогрессом. Таблицы лидеров строятся
только по `stats/{uid}`, который пополняется отправкой забегов.

## Модель данных

```text
logins/{loginKey}                  — уникальность логина
  uid: string

users/{uid}
  login: string                    — как введён при регистрации
  loginKey: string
  createdAt: timestamp

progress/{uid}
  data: object                     — тот же объект, что пишет persistence.js
  schema: 1
  rev: number                      — растёт на 1 при каждой записи
  device: string                   — случайный id устройства
  updatedAt: timestamp

stats/{uid}
  login: string
  all:  { bestTime, bestTimeHero, bestTimeLoad, bestKills, ..., totalKills, totalCodes, games }
  maps: { empty: { ...те же поля }, serverRoom: { ... } }
  lastRun: { map, runId, at }      — защита от повторной отправки одного забега
  updatedAt: timestamp
```

Запрос таблицы: `orderBy('maps.serverRoom.totalKills', 'desc').limit(50)`. Firestore сам
создаёт одиночные индексы для вложенных полей, документы без поля в выборку не попадают —
составные индексы не нужны.

## Правила безопасности (суть)

- Всё, кроме чтения `stats` и `users`, требует входа.
- `logins/{key}`: создать можно только несуществующий ключ на свой uid, у одного uid —
  один ключ; удалять и менять нельзя. Что ключ соответствует служебному адресу из токена,
  правила проверить не могут (в них нет hex-кодирования). Модифицированный клиент может лишь
  занять свободный логин, как при обычной регистрации, — чужой занятый логин он не получит.
- `users/{uid}`: создаёт только владелец, `login` после нормализации (`lower()` и замена
  `ё`) равен `loginKey`, `logins/{loginKey}.uid == uid`. Менять `login` нельзя.
- `progress/{uid}`: читать и писать может только владелец; размер `data` ограничен, `rev`
  только растёт.
- `stats/{uid}`: читают все; пишет только владелец; `login` совпадает с `users/{uid}.login`.
  При обновлении меняются только `all`, `lastRun`, `updatedAt` и одна карта в `maps`
  (`maps.diff(...).affectedKeys().hasOnly([lastRun.map])`), карта из известного списка.
  Итоги не уменьшаются, `games` растёт на 0 или 1, прирост убийств и кодов за одну отправку
  ограничен, рекорды не уменьшаются и не больше разумного предела, прирост в `all` равен
  приросту в карте. Восемь числовых полей обязательны в `all` и в карте; подписи
  рекордов не проверяются (лимит 1000 выражений на запрос).
- Всё остальное запрещено.

Правила хранятся в репозитории (`firestore.rules`) и проверяются тестами на эмуляторе. Список
карт в правилах сверяется с `data/maps/maps.js` контрактным тестом, чтобы новая карта не
отклонялась правилами.

## Синхронизация прогресса

1. **Запуск.** Прогресс читается из `localStorage`, игра стартует сразу, как сейчас.
2. **Вход или регистрация.** После входа читается `progress/{uid}`:
   - облака нет (новый аккаунт) → туда загружается локальный прогресс;
   - локального прогресса нет (новое устройство) → берётся облачный;
   - есть оба и различаются, а устройство ещё не синхронизировалось с этим аккаунтом →
     диалог «Какой прогресс оставить?» со сводкой (коды, победы, герои, время). Без
     автоматического слияния: коды тратятся, и «максимум из двух» дал бы бесплатные коды.
3. **Дальше.** Локальная запись не меняется (`deferSave` в `persistence.js`). Новый слой
   `cloud-progress` раз в 30 с и в конце забега, покупки или сброса отправляет снимок, если
   он изменился. Запись идёт транзакцией: если в облаке `rev` больше последнего известного
   (играли на другом устройстве), выполняется шаг 2 с диалогом.
4. **Выход из аккаунта** не стирает локальный прогресс; устройство просто перестаёт
   синхронизироваться.

Для этого `createProgression` получает два небольших метода: `snapshot()` (текущие данные
для отправки) и `replace(data)` (подставить облачные данные через ту же валидацию, что и при
чтении из `localStorage`). Валидация выносится в отдельную функцию `normalize(saved)`, чтобы
облачные данные проходили те же проверки.

## Этапы

**Этап 1. Каркас и вход.** SDK, `firebase.js`, `login.js`, `auth.js`, флаг включения, панель
аккаунта, окно входа, скрипт сброса пароля. Готово, когда: без `.env` игра и все тесты
работают как раньше; с `.env` можно зарегистрироваться с кириллическим и латинским логином,
выйти и снова войти; «Алёна» и «алена» — один логин; смешанный алфавит, занятый логин и
неверный пароль дают понятные ошибки; сессия переживает перезагрузку.

**Статус на 16.10:** сделано. Кроме перечисленного, в этап вошли правила для `logins` и
`users` (без них регистрация не работает) и `firebase.json`. Проверено тестами на фейковом
Firebase (`tests/test-account.cjs`) и в браузере с эмулятором Auth: панель, ошибки, вход
логином в другом регистре, откат аккаунта при сбое записи профиля, сессия после перезагрузки,
вёрстка на 375 px. Регистрация на настоящем проекте проверена владельцем.

**Этап 2. Правила и тесты на эмуляторе.** `firestore.rules`, `test:rules` (нужна Java для
эмулятора, поэтому вне `npm test`; в CI — отдельный шаг). Готово, когда: чужой логин не
занять, чужой прогресс не читается, уменьшение итогов, прирост `games` больше 1, правка двух
карт сразу и неизвестная карта отклоняются.

**Статус на 16.10:** сделано, 12 тестов в `tests/rules/firestore-rules.cjs` проходят на
эмуляторе; в CI — шаг с Java 21 после smoke. Что выяснилось:

- `lower()` в правилах меняет регистр только у латиницы. Ключ логина из кириллицы правила
  считают цепочкой `replace()` по каждой заглавной букве. Правила, выкаченные на этапе 1,
  отклоняли регистрацию с заглавной кириллицей — их нужно выкатить заново.
- Запрос может вычислить не больше 1000 выражений. Поэтому числовые поля статистики
  обязательны (клиент всегда шлёт все), а подписи рекордов (герой, нагрузка) правила не
  проверяют: клиент показывает только известные ему id героев и нагрузку 1–10.
- `tests/test-firestore-rules.cjs` (в `npm test`) сверяет список карт в правилах с
  `data/maps/maps.js`.

**Этап 3. Облачный прогресс.** Рефакторинг `persistence.js`, `cloud-progress.js`, диалог
выбора. Готово, когда: прогресс переносится на второй браузер, конфликт показывает диалог,
офлайн ничего не ломает.

**Статус на 16.10:** сделано. `normalizeProgression` вынесена из `createProgression`,
у прогресса появились `replace()` и `onChange()`: уведомляют только сохранения после
покупок и итогов забега (`'save'`) и уход со страницы (`'hidden'`), доход в бою — нет.
Синхронизация ждёт 5 с после изменения (собирает пачку сохранений конца забега), при уходе
со страницы — сразу; без сети показывает «ОБЛАКО НЕДОСТУПНО» и повторяет через минуту.

## Риски

- **Логин виден в таблице**, значит аккаунт защищает только пароль. Firebase Auth сам
  ограничивает перебор (`auth/too-many-requests`); для игры этого достаточно.
- **Похожие логины.** Запрет смешения алфавитов отсекает подмену букв внутри логина, но
  «Vasya» и «Вася» — разные логины.
- **Забытый пароль** без почты сбрасывает только владелец, скриптом.
- **Подделка результатов.** Правила отсекают невозможные значения и прирост, но не
  модифицированный клиент. Если таблицы станут важными — Cloud Function с проверкой по `seed`
  и журналу забега (тариф Blaze).
- **Накрутка итогов** честной игрой (много коротких забегов) не запрещена: это и есть
  «всего игр». Отсекаются только забеги короче 10 секунд.
- **Конфликт прогресса** при игре на двух устройствах одновременно — решается диалогом, не
  тихим слиянием.
- **Размер бандла:** auth + firestore/lite ≈ 100–130 КБ gzip, грузятся после меню.
- **Квоты Spark** (50 тыс. чтений и 20 тыс. записей в день). Одна таблица — до 51 чтения;
  забег — 1 чтение и 1 запись статистики плюс запись прогресса. С кэшем на 60 с это сотни
  активных игроков в день. Если упрёмся — снимок топов раз в несколько минут в одном
  документе (нужна Cloud Function) или тариф Blaze.
