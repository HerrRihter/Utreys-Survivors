План внедрения экспериментальной учебной карты
=============================================

Дата: 20 октября 2026 года. Статус: прототип реализован 21 октября 2026 года, этапы 0–8 выполнены; открытые вопросы — в пункте 15.

Цель: добавить одну карту с мини-тестами для продвижения, бонусов и одной попытки возрождения. Реализация расширяет действующие модули и контракты проекта. Изменение архитектуры, новый игровой движок, отдельное приложение и замена системы состояния не входят в работу.

Основание: [контракт структуры](STRUCTURE-CONTRACT.md), [машинная матрица](../tools/structure-contract.json), [техническая документация](../documentation.md) и чтение текущих исходников. При расхождении этого плана с контрактом приоритет имеет контракт; расхождение необходимо разрешить до реализации соответствующего этапа.

**1. Зафиксированный объём первой версии**

Карта «Учебный полигон: партионный учёт», технический ID `learningLab`, доступна сразу и помечена как экспериментальная. По уточнению пользователя карта физически состоит из нескольких комнат и отдельного помещения босса. Для прототипа приняты три последовательные учебно-боевые комнаты и четвёртая комната с новым боссом «Партионный учёт». Тест в каждой учебной комнате открывает переход дальше. Дополнительно есть один необязательный бонусный терминал. Босс выглядит как множество склеенных значков Пепси, сам атакует и регулярно призывает вокруг себя обычных юнитов Пепси. Подробная интеграция комнат и босса определена в пункте 14 и обязательна для первой версии.

| Сценарий | Правило | Результат |
| --- | --- | --- |
| Обязательный терминал | 3 вопроса, минимум 2 правильных | Терминал завершён, открыт следующий |
| Бонусный терминал | 1 вопрос, одна попытка за забег | При успехе лечение |
| Смертельный урон | Предложение теста: 3 вопроса, минимум 2 правильных | Одно возрождение: 50% HP, 3 секунды неуязвимости |
| Провал обязательного теста | Разбор ошибок, повторная попытка | Продвижение остаётся закрытым |
| Провал или отказ от возрождения | Окончательное завершение | Обычный экран поражения с учебной статистикой |

Параметры задаются данными. Для прототипа: 10 учебных очков за первый правильный ответ на вопрос в забеге; лечение на 20% максимального HP за успешный обязательный терминал и на 25% за бонусный. Лечение ограничено максимальным HP и использует действующий коэффициент лечения. Возрождение устанавливает долю HP напрямую, как отдельная механика.

Очки обучения не являются кодами аккаунта. Повторный ответ на уже вознаграждённый вопрос очков не добавляет. Награда терминала выдаётся один раз. Повторное прохождение после ошибок разрешено; первая попытка и последующие считаются отдельно.

Первый прототип использует лечение и существующее поле неуязвимости. Новые временные модификаторы характеристик, выбор оружия за ответ, постоянная учебная валюта, LMS, редактор курсов и автоматическая оценка свободного текста отложены. Это ограничивает число изменяемых подсистем без сокращения трёх основных учебных сценариев.

**2. Архитектурные инварианты**

| Область | Обязательное правило |
| --- | --- |
| Слои | Матрица импортов остаётся прежней; новые верхнеуровневые каталоги и исключения не добавляются |
| React | Читает представления и вызывает команды `app`; не импортирует `data`, `systems`, `core` даже через `import type` |
| Механика | Проверка ответов, попытки и награды находятся в `systems`; никаких DOM, Canvas, React или сетевых запросов |
| Координация | Режимы, ввод, сохранение и уведомления UI координирует `app`, композиционный корень — существующий `GameSession` |
| Отрисовка | Терминалы рисуются в `rendering`, геометрия и статусы поступают через состояние и чистые `systems/queries` |
| Контент | Тексты, правильные ответы, темы и параметры находятся в `data`; механика выбирается по `kind`/`type`, не по ID карты или вопроса |
| Модель | Все поля `run.state` существуют с момента создания и перечислены в `runFields`; временное добавление полей запрещено |
| Случайность | Выбор вопросов и перемешивание ответов используют `state.rng`; представления и рендер не расходуют RNG |
| Время | Существующий фиксированный шаг сохраняется; при тесте симуляция и игровые таймеры остановлены |
| Хранилище | Только `persisted()` и существующий снимок забега; изменение формата сопровождается миграцией |
| Зависимости | Фабрики и явная передача зависимостей; никаких глобальных экземпляров или второго состояния игры в React |
| Проверки | Общие suites не отключаются, машинные проверки не ослабляются ради новой карты |

Поправка к предварительной концепции: отдельный поток случайности для динамических вопросов не вводится. Имеющиеся отдельные генераторы размещения узлов и плана событий сохраняются; учебная механика во время забега работает через `state.rng`. На обычных картах учебная логика не должна расходовать RNG.

Существенные особенности текущего кода:

- `updateNodes()` пытается создать охранника для каждого `guarded`-узла. Учебный терминал должен обрабатываться своей веткой до этого участка.
- `allNodesResolved()` признаёт только `destroyed` и `workaround`. Для учебного завершения требуется явное правило, а не подмена статуса на `destroyed`.
- HUD и указатели используют предположение, что незавершённый узел обязательно `guarded`. После введения новых статусов все эти потребители переводятся на общие запросы.
- `snapshotRun()` сейчас отвергает HP <= 0. Одного добавления нового экрана недостаточно для сохранения теста на возрождение.
- `resume()` открывает level-up либо паузу; восстановление теста нужно добавить явно, до возможности продолжить бой.
- RAF не шагает вне `play`, но публичный `session.update(dt)` вызывает шаг напрямую. Новый режим должен быть защищён и на этом пути без нарушения действующих тестовых сценариев.
- `finish()` выдаёт бонусы и фиксирует результат сразу. Отменять уже записанное поражение ради возрождения нельзя.
- Firestore содержит явный список карт, а тесты сопоставляют его с данными. Добавление карты требует согласования этой проверки и политики рейтинга.

**4. Банк вопросов и правила контента**

Новые файлы в существующем корне `data`: `learning-questions.js` и `learning-rules.js`. Новая папка `data/learning` не нужна: список разрешённых каталогов остаётся прежним.

Каждый вопрос содержит стабильный ID, исходный номер, тему, тип (`single`, `multiple`, `open`), текст, варианты со стабильными ID, правильные ID, исходные веса, пояснение и статус готовности. Курс содержит ID, версию, название, памятки по темам и состав вопросов. Правила содержат пороги, число вопросов, размер наград и лимит возрождений.

Исходный материал: 26 вопросов — 23 с одним ответом, 1 с несколькими, 2 открытых. Положительный вес означает правильный вариант; значение веса хранится как свойство исходного теста и не превращается автоматически в размер игровой награды. Вопрос № 10 имеет тип множественного выбора при одном положительном варианте: сохранить исходные данные и отметить это в проверке контента, не добавлять выдуманный второй ответ.

Для закрытых вопросов: один ответ — точное совпадение; несколько — точное совпадение множеств без частичного зачёта и без зависимости от порядка. Пустой выбор не подтверждается, неизвестные ID отклоняются. Варианты перемешиваются при создании попытки и сохраняются, затем остаются неизменными.

Открытые № 4 и № 21 сохраняются как материал для самопроверки, не попадают в обязательный, бонусный или восстановительный пул. Для них нужны проверенные эталоны. Пояснения и памятки также отсутствуют в исходнике: подготовить черновики из предоставленного материала, отметить неподтверждённые сведения, включать в опубликованный учебный пул только готовый контент. Актуальность регламентов и проектных фактов подтверждает владелец курса; это контентная зависимость, не повод останавливать разработку движка.

Валидатор проверяет уникальность ID, ссылки, типы, корректность правильных вариантов, положительность параметров, достаточность вопросов для каждой темы и согласованность версии. Готовые закрытые вопросы обязательно имеют пояснение. Тесты включают отрицательные примеры невалидного банка.

**5. Модель целей и размещение карты**

Добавить тип цели `learning` и вид узла `learning-terminal`. Использовать существующий массив `state.nodes`, не создавать второй параллельный массив целей. Учебные узлы имеют признак обязательности, тему и порядковый номер этапа. Данные попыток и ответов находятся только в `state.learning`.

Новые состояния учебного узла: `locked`, `available`, `completed`, `exhausted`. `exhausted` используется для израсходованного бонусного терминала. Обычные `guarded`, `destroyed`, `workaround` остаются с прежней семантикой. Для узлов без признака обязательности действует прежнее правило: они обязательные.

Чистые запросы определяют, завершён ли узел, требуется ли он для босса и доступен ли для взаимодействия. `allNodesResolved()` остаётся совместимым входом для текущих callers и использует общую семантику обязательных целей. Рендер обращается к `queries`, не импортирует изменяющие состояние системы.

Учебная ветка размещения использует текущие зоны, расстояния и коллизию. Проверить получение всех четырёх терминалов, доступность проходов и отсутствие пересечений со стойками. Если случайное размещение не удалось, использовать проверенные резервные позиции этой карты; нельзя тихо создать меньше целей или подставить пять обычных узлов.

В пределах радиуса доступного терминала HUD предлагает кнопку «Начать тест», общую для мыши и touch. Команда заново проверяет расстояние и доступность. Автоматическое открытие при приближении не требуется. Новая клавиша взаимодействия и миграция настроек клавиш не нужны.

**6. Модель учебного состояния и системы**

В `RunModel`, фабрику и `runFields` добавить `learning: null | LearningState` с категорией `save`. На обычных картах значение всегда `null`. На учебной карте структура полностью создаётся в начале забега.

`LearningState` хранит версию курса, номер следующей попытки, активную попытку или null, использованную возможность возрождения, статистику по вопросам/темам, учебные очки и уже выданные награды. Активная попытка хранит причину (`progress`, `bonus`, `revive`), ID терминала при наличии, фазу, список вопросов, порядок вариантов, текущий индекс, выбранные ID, подтверждённые ответы, результат и признак применения результата.

Фазы попытки: предложение/памятка → вопрос → обратная связь → следующий вопрос или итог → применение результата → закрытие. После подтверждения ответ неизменяем. Правильные ответы доступны в представлении только на фазе обратной связи.

План новых модулей:

- `src/systems/learning.js`: фабрика состояния, проверка доступности, создание попытки, проверка ответа, переходы и статистика.
- `src/systems/learning-rewards.js`: ограниченные текущим забегом награды, повторная выдача исключена.
- `src/systems/queries/learning.js`: чистые запросы доступности, результата и прогресса, без импорта изменяющих систем.
- `src/app/learning-flow.js`: режим, сброс ввода, сохранения, звук, обновление UI, завершение попытки.
- `src/app/views/learning.js`: данные экрана без бизнес-логики.
- `src/components/LearningScreen.tsx`: существующий `Overlay`, формы вариантов и кнопки.

Если объём кода не оправдывает отдельный файл наград, его функции остаются в `learning.js`; это не основание создавать общий framework тестирования или наград.

Создание механики — через текущий `createRunSystems`/`GameSession`, зависимости передаются явно. `GameFlow` собирает `learning-flow` рядом с lifecycle и level-up. Циклические импорты между lifecycle и учебным контроллером запрещены; нужные callbacks связываются в композиции.

**7. Переходы экранов, поражение и конкурирующие события**

Расширить `RunState.mode` значением `quiz`. Фазы теста находятся в учебном состоянии, не вводить отдельный глобальный mode для каждого вопроса. React не хранит авторитетные ответы, прогресс и награды в `useState`.

| Событие | Переход и обязательное действие |
| --- | --- |
| Взаимодействие в `play` | Проверить дистанцию, статус и отсутствие другого диалога; создать попытку; `quiz`; сбросить ввод; сохранить |
| Выбор/подтверждение | Проверить phase и ID попытки; обновить модель; сохранить; уведомить UI |
| Верный/неверный ответ | Показать объяснение; ждать явного продолжения, бой не возобновлять |
| Успех обязательного теста | Однократно завершить терминал и применить награду; открыть следующий; сохранить; продолжить |
| Провал обязательного теста | Предложить повтор или возврат в бой; терминал остаётся доступен |
| Смертельный исход | Если шанс доступен — создать предложение возрождения, зафиксировать расход попытки, перейти в `quiz` без записи поражения |
| Успех возрождения | Установить HP, неуязвимость, сбросить движение и состояние удара героя; сохранить до продолжения |
| Провал/отказ от возрождения | Применить окончательное `finish(false)` ровно один раз |
| Повторный смертельный исход | Сразу обычное поражение |
| Уход в меню/перезапуск | Действующий lifecycle завершает забег один раз; при открытом возрождении исход — поражение |

Предлагаемый API команд: `startLearningTest(nodeId)`, `selectLearningAnswer(attemptId, optionId)`, `submitLearningAnswer(attemptId)`, `advanceLearning(attemptId)`, `retryLearning(attemptId)`, `closeLearning(attemptId)`. Названия можно уточнить без изменения границ ответственности. Старая команда с чужим attemptId или недопустимой фазой не меняет состояние.

Существующий конец шага задаёт приоритет: смерть → победа → level-up. Сохранить его. Учебный тест терминала начинается по команде вне шага; при наличии накопленного level-up сначала открыть его. После теста перед возобновлением симуляции проверить отложенную победу и level-up. При одновременной смерти героя и босса предложение возрождения обрабатывается первым; после успеха — победа без дополнительного боевого шага.

Симуляция не открывает UI из середины цикла врагов или спавна. Смертельный исход передаётся в flow существующим механизмом callbacks; окончательный `finish` отделяется от предложения восстановления. Нельзя использовать уже завершённый `end` как временную паузу и затем сбрасывать `resultRecorded`.

Проверить Escape, Q/E, цифровые клавиши level-up, удержание движения, pointer capture и touch-стик. В `quiz` они не должны управлять боем или закрывать тест в обход правил. Escape не переводит автоматически в `play`; выход выполняется явной кнопкой с семантикой текущего сценария. Не добавлять глобальный запрет стандартных клавиш формы.

**8. Сохранение и совместимость**

Новая версия снимка — v5, ключ `utreys-run-v5`. Старый v4 включается в `LEGACY_RUN_SNAPSHOT_KEYS`; сохраняется цепочка v1 → v2 → v3 → v4 → v5. Миграция v4 добавляет `learning: null`, сохраняя формат graph-json, общие ссылки и RNG. Отдельно проверить reduced-снимки v1–v3 и полноценный v4.

Источник активного теста — `state.learning.active`; не дублировать весь тест ещё и на верхнем уровне снимка. Восстановление: активный тест → `quiz`; иначе pending level-up → `level`; иначе обычная пауза. Порядок вопросов и вариантов после загрузки не пересоздаётся.

Разрешить HP = 0 только для валидного незавершённого сценария возрождения: учебная карта, правильная версия курса, активная восстановительная попытка, израсходованный шанс и отсутствие окончательно записанного результата. Остальные мёртвые забеги по-прежнему не сохраняются и не возобновляются.

Добавить `quiz` в сохранение при `pagehide`. Сохранять также на открытии, подтверждении ответа, переходе, выдаче награды и закрытии попытки: текущий 30-секундный таймер игрового времени во время теста не работает. Выбор варианта можно сохранять сразу — это редкое дискретное событие.

Изменение награды, отметки о её получении и фазы выполняется синхронно, затем записывается один цельный снимок. Повторное подтверждение и повторное восстановление не должны повторять награду. Ошибка записи не должна падать исключением: показать, что продолжение после закрытия вкладки не гарантируется; работа в памяти остаётся доступной. Локальные сохранения не дают защиты от ручного редактирования или отката файлов пользователем.

Проверить отказоустойчивость `resume()`: сейчас оно вызывает `start()`, очищающий снимок. При расширении восстановление не должно уничтожать единственную копию до успешной проверки и пересохранения.

Курс версии 1 после выпуска неизменяем в отношении ID, правильных ответов и смысла вопросов. Изменение смысла выпускается новой версией; используемая незавершёнными забегами версия остаётся доступной. При неизвестной версии нельзя молча проверять старые ответы по новому банку: сохранить исходный снимок и показать невозможность продолжения с предложением нового забега.

**9. Награды аккаунта, статистика и облако**

Для первого выпуска зафиксировать ограниченную политику: учебные награды действуют только в забеге; стандартные коды, убийства и факты применения умений от обычного боя продолжают обрабатываться существующими модулями прогрессии. Полная изоляция экономики учебной карты не заявляется и потребовала бы отдельной работы. Прямые записи в `progression.data` запрещены.

Учебный результат не участвует в соревновательной статистике `runStats`/лидерборде, не открывает следующую нагрузку, победные открытия обычных карт и режим «Продакшен». Политика задаётся данными карты с прежними значениями по умолчанию для остальных карт. Обновить `countRun`, `recordRun`, бонусы `finish`, `resultView` и защиту команды `continueProduction` согласованно. Не ограничиваться скрытием кнопки.

У учебного забега остаются `resultRecorded` и однократная запись в локальный журнал. Не вызывать для него итоговые `recordTime`, `recordKills`, `recordLevel`, `recordRunStats`, `recordRunResult`, открывающие обычные рекорды/победы. Ранее накопленные боевые факты и доход не откатывать.

Добавить сводку обучения в существующий run-log: курс/версия, число правильных первых ответов, число повторов, результаты по темам, очки и возрождение. Поскольку меняется сохраняемый формат журнала, версионировать записи и добавить нормализацию старых записей без учебного блока; обновить экспорт и `tools/run-stats.cjs`. Сохранить ограничение размера журнала; ответы не накапливать бесконечно при повторных попытках. Для статистики достаточно счётчиков по конечному набору вопросов и текущей попытки.

Не создавать новый Firebase-сервис. Проверить, что учебный забег не формирует событие отправки результата, гостевую отложенную отправку и запись в офлайн-очереди. В `normalizeRunEntry` добавить проверку допуска карты к рейтингу, чтобы фильтрация работала также для восстановленных очередей.

Firestore: актуализировать допустимые рейтинговые карты и тест сопоставления так, чтобы список правил равнялся именно картам, допускаемым политикой к рейтингу. Новая учебная карта в этот список не входит. Добавить положительный тест прежних карт и отрицательный тест попытки записи учебного результата; не ослаблять правила `hasOnly`/проверки роста статистики. Если изменяются сами правила — запуск эмуляторных тестов обязателен.

Учебная история в прототипе локальная, через журнал. Синхронизация результатов обучения между устройствами не входит в первый выпуск; стандартная облачная прогрессия аккаунта продолжает работать.

**10. Интерфейс и отрисовка**

Экран теста показывает тему, цель попытки, номер вопроса, тип выбора, формулировку и варианты. Подтверждение — отдельной кнопкой. После ответа отображаются результат и объяснение. Перед тестом — памятка; у возрождения сначала явное предложение с ценой ошибки: забег закончится при провале.

Использовать существующий `Overlay` для удержания и возврата фокуса, семантические radio/checkbox и подписи, доступные сообщения обратной связи. Длинные вопросы прокручиваются внутри панели, кнопки остаются достижимыми на телефоне. Нет лимита времени на чтение и ответ. В состоянии `quiz` не показывать поверх теста `ConflictDialog`; существующий конфликт облака можно решить после выхода из теста.

Все стили — `styles/game.css`, существующие семантические токены. Canvas-терминал строится текущими средствами отрисовки; новые растровые ресурсы и пакеты не требуются. Цвет и значок дополняются текстовым статусом.

HUD: завершённые обязательные терминалы / 3, доступная тема, учебные очки и оставшийся шанс возрождения. Итоги: первые ответы отдельно от повторов, ошибки по темам, награды, факт восстановления. Сообщения про обычные рекорды и доступность продакшена должны учитывать политику карты.

Предпросмотр арены, радар и стрелки используют корректные цели выбранной карты. Недоступные следующие терминалы не считаются завершёнными; необязательный терминал не блокирует босса.

**13. Условия завершения, выпуск и откат**

Готовность означает полный цикл: первая комната и тест → вторая комната и тест → третья комната и тест → комната босса «Партионный учёт» → учебный итог, а также все исходы бонуса и возрождения. После закрытия вкладки продолжается та же попытка в той же комнате, награды не повторяются. Обычные карты сохраняют исходное поведение и RNG. Матрица импортов и ограничения Canvas/random/storage проходят без новых исключений.

Перед включением карты проверить готовность контента, обновить описания карт и снимков в `documentation.md`, пользовательский сценарий в README и действующий контракт хранения с новым ключом v5. Этот документ оставить планом с отмеченными выполненными этапами либо переработать в описание механики после приёмки.

Предусмотреть управляемую данными доступность карты для новых забегов. При отключении эксперимента определение карты, курс и загрузчик снимков остаются в сборке, чтобы закончить начатое. Учесть проверку `mapOpen` в `start()` при `resume()`: запрет нового старта не должен подменять карту сохраняемого забега на `empty`.

Откат через отключение новых стартов предпочтителен откату бинарной версии: сборка без поддержки v5 не обязана уметь читать новые сохранения. Обратная миграция v5 → v4 не входит в план и не должна имитироваться сменой номера версии.

Работа ограничена одной картой и расширением существующих точек ответственности. Любое требование нового слоя, глобального реестра событий, нового state-manager или перестройки всех целей считается выходом за этот план и требует отдельного архитектурного решения.

**14. Обязательное уточнение: комнаты и босс «Партионный учёт»**

Этот пункт уточняет первоначальную концепцию единой арены. Комнаты, уникальный босс, составной облик из значков Пепси и периодический призыв обычных Пепси — требования пользователя. Точное количество комнат, способ перехода и численный баланс ниже — предлагаемые решения для прототипа.

| Помещение | Содержание | Условие выхода |
| --- | --- | --- |
| 1. Основы партионного учёта | Бой с обычными врагами, памятка и тест по структуре номера партии | Успешный обязательный тест открывает переход в комнату 2 |
| 2. Резервирование | Бой, тест по резервам и производственному заказу, необязательный бонусный терминал | Успешный обязательный тест открывает переход в комнату 3 |
| 3. Ошибки и исключения | Бой, тест по ошибкам и обработке нестандартных ситуаций | Успешный обязательный тест открывает переход в комнату босса |
| 4. Партионный учёт | Новый босс и призываемые им обычные Пепси | Убийство босса завершает карту победой |

Это физически отдельные помещения с собственными границами и точками появления, а не визуальное переименование терминалов на открытой арене. Для сохранения текущей геометрической модели предлагается разместить четыре помещения внутри существующего мира 2200 × 2200, разделить их статическими стенами из прямоугольников `racks` и связать явно активируемыми переходами. Переход переносит героя в безопасную точку следующей комнаты после успешного теста. Динамические двери и перестройка коллизии в первой версии не требуются.

Переходы однонаправленные. Пока тест не пройден, команда перехода недоступна; после успеха игрок активирует переход отдельно. Случайное касание терминала не переносит героя. Бонусный терминал можно пропустить, его прохождение не открывает обязательный переход.

Данные карты дополняются описаниями комнат: ID, границы, точка входа героя, точки/зоны спавна, размещение терминалов, переход и следующая комната. Босс получает заданную безопасную точку в финальном помещении. Четыре терминала размещаются в назначенных комнатах, а не распределяются случайно по всем зонам карты. Существующий генератор остальных карт остаётся прежним.

Авторитетное состояние продвижения хранится в `state.learning`: `roomIndex` и флаги выполненных переходов создаются сразу в фабрике и сохраняются в v5. Геометрия комнат находится только в данных карты/арене; активная комната определяется состоянием забега, а не изменяемым глобальным кэшем арены. `world` отвечает за геометрию и допустимость позиции, `systems` — за правила перехода, `app` — за команду, сброс ввода и сохранение.

Проверить и расширить существующие точки:

- `src/world/arenas.js`: предоставление геометрии комнат при прежней коллизии прямоугольников. Начальная позиция героя берётся из данных карты, а не всегда из центра мира. Навигационное поле использует актуальную позицию игрока и геометрию; переход не должен оставлять устаревший путь из прежней комнаты.
- `src/systems/run-model.js`, `run-layout.js`: начальная комната, вход героя, терминалы внутри соответствующих помещений.
- `src/systems/queries/learning.js`: текущая комната, доступный переход, состояние допуска к финальной комнате.
- `src/systems/enemy-spawning.js`: обычные волны и позиционный спавн ограничены активной комнатой. Существующее размещение на расстоянии 520–640 px от героя может оказаться за её стенами, поэтому для комнат нужны свои зоны и ограниченное число попыток размещения. При отсутствии места спавн откладывается, а не происходит в закрытом помещении.
- `src/systems/learning.js`: проверка и применение перехода. Сохраняются HP, сборка, опыт, RNG, общий игровой таймер и результаты тестов. На границе комнаты удаляются оставшиеся враги, их снаряды, опасные зоны и временные объекты предыдущего боя без наград за убийство; наземные неполученные предметы не переносятся. Очистка выполняется явным списком полей модели и проверяется тестами. Временные состояния героя, ссылающиеся на прежние цели/опасности, очищаются согласованно; глобального сброса сборки и cooldown нет. UI сообщает, что переход оставит неполученные предметы.
- `src/app/learning-flow.js`, `session-commands.js`: команда перехода с повторной проверкой расстояния, допуска, режима и номера комнаты; двойная команда не переносит через две комнаты. После перехода сбросить ввод и записать цельный снимок.
- `src/rendering/arena-floor.js`, `node-objectives.js`, `edge-arrows.js` и preview-kit: стены, подписи помещений, переходы и указатель внутри активной комнаты. Камера и предпросмотр должны ясно показывать комнатную структуру.

Все изменения работают по наличию конфигурации комнат/виду поведения, без сравнений с ID `learningLab`. Общий таймер волн продолжается; после перехода не накапливается залп отложенных спавнов. В последней комнате обычные волны отключаются данными: основной источник новых обычных врагов — призыв босса. Эта политика проверяется отдельно от условий появления самого босса.

Финальный босс:

- Новая запись в `data/enemies/units.js`, предлагаемый ID `batch_accounting`, имя **«Партионный учёт»**, `boss: true`.
- Самостоятельный атакующий противник, не пассивный сервисдеск. Для прототипа использовать имеющийся вид обычной атаки `pulse` с предупреждением перед ударом и отдельную периодическую способность призыва. Численные HP, радиус, скорость и урон настраиваются в данных с учётом размера комнаты и текущих множителей сложности.
- Призыв использует уже существующее поле `summon` и `summonAround()` из `enemy-behaviors.js`: `units: ['pepsi']`, предлагаемые стартовые параметры — 3 юнита раз в 7 секунд, не более 12 живых от этого босса. Это параметры балансировки, а не дополнительные требования пользователя.
- Призываются именно обычные Пепси с их действующим поведением, не новые копии определения юнита и не дополнительные боссы. `summonerId` связывает каждого призванного врага с боссом. Убийство Пепси освобождает место под следующий призыв.
- Размещение вокруг босса учитывает его радиус, стены, границы текущей комнаты и радиус призываемого юнита. При нехватке места призвать меньше, без размещения внутри стен или в соседнем помещении; ограничить число попыток. Для обычных карт существующее поведение призыва должно сохраниться.
- Призыв и обычные атаки имеют свои существующие таймеры и продолжают работать совместно. Во время теста на возрождение оба остановлены. После загрузки не вызывается дополнительная бесплатная волна.
- Новый босс указан только в расписании учебной карты. Условие появления: все обязательные тесты пройдены **и** герой перешёл в последнюю комнату. Для карт без комнат прежнее условие `all-nodes-resolved` не меняется. Новое условие и его допустимые данные явно проверяются в `tools/check-game-contracts.cjs`; проверка условий не удаляется.
- Победа наступает при смерти босса; оставшихся призванных Пепси добивать не требуется. Общая обработка смерти босса и приоритет одновременной смерти героя сохраняются.

Внешний вид: крупная неровная масса из многих перекрывающихся, как будто склеенных друг с другом значков Пепси. Силуэт должен отличаться от увеличенного одиночного значка и от сервисдеска. Использовать текущий Canvas-арт: новую запись `unitArt` в `src/rendering/art/enemy-art.js` и переиспользование примитива эмблемы из `client-emblems.js`. Композиция эмблем задаётся фиксированными смещениями и масштабами; при рисовании не расходовать игровой RNG. Для создания такого арта не нужен ImageGen или отдельный ресурсный pipeline.

Проверить размер кешируемого спрайта в `src/rendering/enemies.js`, отсутствие обрезания крайних эмблем, попадания, тень, подпись и полосу HP. Если размер выбирается данными, добавить соответствующее свойство определения, не ветвление по ID в рендерере. Запись в `data/enemies/bestiary.js` описывает босса и призыв, числа берутся из `unitDefinitions`. Новые реплики добавляются в существующий справочник только при необходимости.

Дополнение к этапам: данные комнат/босса проектируются на этапе 1; поля комнаты и миграции — на этапе 2; переходы — на этапе 3; физическая карта, спавн и босс — на этапе 4; команды перехода — на этапе 5; составной арт, HUD и предпросмотр — на этапе 6. До приёмки эксперимент не включается без любого из этих элементов.

Дополнительные критерии приёмки:

- Нельзя пройти стену или перейти в следующую комнату без успешного теста; после загрузки это ограничение сохраняется.
- Переход не меняет сборку и не выдаёт награды за оставленных врагов; повторная команда не пропускает комнату.
- Враги, Пепси, снаряды и опасности не появляются в закрытых комнатах; нет застревания в стенах и недостижимых терминалов.
- Босс не возникает в третьей комнате после последнего ответа, а появляется однократно в четвёртой после перехода.
- На экране и в бестиарии имя «Партионный учёт»; визуально читается склеенная масса многих значков Пепси.
- Босс сам наносит обычные атаки и многократно призывает обычных Пепси вокруг себя; лимит живых призванных соблюдается.
- Снимок сохраняет комнату, босса, его таймер призыва, существующих Пепси и `summonerId`; восстановление не удваивает призыв.
- Replay включает переходы комнат, призывы, тест на возрождение в бою с боссом и загрузку посередине боя.

**16. Лабиринты (21 октября 2026 года)**

Заменяет комнаты пункта 14 и бонусный терминал. Цель — чтобы путь к терминалу был боем и поиском.

- Карта — три лабиринта и центральный зал. Каждая комната занимает всю арену 2200 × 2200; переход через дверь заменяет арену следующей (`world.follow`, `arenas.forRoom`).
- Лабиринт генерируется из сида забега и номера комнаты (`src/world/maze.js`): сетка 10 × 10 клеток по 220 px, стены 36 px, рекурсивный backtracker и 15% тупиков раскрыто в петли. Вход — в случайном углу. Три терминала — в самых далёких друг от друга внутренних клетках (с небольшим разбросом, тупики предпочтительны), дверь — во внутренней клетке не ближе трети лабиринта к ним. Тот же сид — тот же лабиринт, продолжение сохранения возвращает тот же.
- У каждого терминала страж — случайный баг из ростера узлов, стоит в коридоре перед ним. Терминал открывается, когда страж побеждён или найден воркэраунд (6 с в круге без урона), как у обычного узла.
- Пройденный тест кладёт у терминала пакет обновлений (один раз за терминал). Каждая ошибка, даже в пройденном тесте, вызывает проверку: пачку из 3 врагов текущих волн рядом, не больше 2 пачек за тест.
- Дверь открывается, когда пройдены все три терминала; стрелка у края экрана ведёт к ней. К терминалам стрелок нет: их нужно найти.
- Сила врагов растёт по лабиринтам (×1, ×1,3, ×1,6), размер волн и их лимит тоже; во всех лабиринтах приходит весь ростер. Волны появляются в 420–900 px от героя.
- Центральный зал: четыре колонны, босс «Партионный учёт» в центре.
- Формат учебного состояния: `layout: 2` и `audits`; сохранения прежних комнат продолжить нельзя (честный отказ с сообщением, как при неизвестной версии курса).

**17. Вторая учебная карта: «Полигон инцидентов» (21 октября 2026 года)**

Та же схема (пункт 16), другой курс. Карта `incidentLab`, курс `critical-incidents` (`data/learning-incidents.js`), босс «Критический инцидент».

- Карта называет свой курс в `objective.course`; реестр курсов — `data/learning-courses.js`, код берёт курс по карте (`courseOf`). Комнаты обеих карт строит одна функция в `data/learning-rules.js`: три лабиринта (темы 0–2) с тем же ростом силы и центральный зал.
- Курс собран скриптом из сохранённой страницы результатов Google Forms «Тестирование по управлению критическими инцидентами»: 40 вопросов — 25 с одним ответом, 8 с несколькими, 7 открытых. Ключи — отмеченные «Правильно» ответы при полном балле и блоки «Правильный ответ» для шести ошибочных ответов; пояснения — комментарии автора теста, где они есть, иначе формулировка ключа. Комментарии открытых вопросов — эталоны для самопроверки. Имя и почта прошедшего не сохраняются.
- Темы: «Критичность и роли» (9 закрытых), «Трекер и эскалация» (11), «Коммуникации и разбор» (13). Памятки тем составлены по ключам и комментариям теста.
- Босс «Критический инцидент» — коллаж логотипов клиентов (поле `collage` юнита, общий рисовальщик; так же теперь нарисован «Партионный учёт»), призывает Пепси, Марс и Балтику.
- Учебное состояние хранит `course`; сохранения первой карты без этого поля продолжаются как её курс.

**18. Плотность, боссы, штраф за провал и оценка (21 октября 2026 года)**

- Волны в лабиринтах вдвое плотнее: `batch` 4 и `cap` 28 в `learningSchedule` (`data/enemies/waves.js`), пачка проверки за ошибку — 6 врагов (`auditPack`). Обычные карты не затронуты: хэши повторов (`node tests/helpers/replay-child.js`) совпадают.
- Учебные боссы усилены и получили особые приёмы — см. [ENEMIES-AND-NODES](ENEMIES-AND-NODES.md#учебные-боссы).
- Награда терминала зависит от счёта (`terminalRewards`): 3 из 3 — пакет обновлений и капсула лечения, 2 из 3 — только капсула. Проваленный тест (или брошенный после первого ответа) закрывает терминал на 10 с (`failLock`, поле узла `retryAt`) и на 20 с усиливает волны в 1,5 раза (`surge`, поле `learning.surgeUntil`). HUD и терминал показывают обратный отсчёт.
- Итоги учебного забега — оценка: вопрос даёт 100% при верном ответе с первой попытки, 60% со второй, 30% с третьей и позже, 0 — если не решён (`learningGrading`). Средний процент переводится в «Отлично» (≥ 90%), «Хорошо» (≥ 75%), «Удовлетворительно» (≥ 60%) и «Не сдано». Экран итогов показывает оценку, проценты по темам и каждый заданный вопрос: с какой попытки решён, сколько было попыток, ошибочные варианты, а для решённых не с первого раза — ключ и пояснение. При поражении оценка помечена как промежуточная. Запись ответа хранит `firstCorrectAt`, `wrong` и `sources`; журнал забегов получает сводку без текстов.
- Снимок забега — v6 (`utreys-run-v6`): миграция v5 добавляет `retryAt`, `surgeUntil` и поля записей ответов.
- Пояснения без вводных «По предоставленному учебному материалу» и «По регламенту…» (их запрещает `validateLearningCourse`), голые ключи переписаны фразами; памятки тем описывают, о чём тема, без конкретных значений из ответов. Версия курсов не менялась: ID вопросов и ключи прежние.

**19. Одна карта «Учебный центр» и выбор курса (21 октября 2026 года)**

- Карты `learningLab` и `incidentLab` заменены одной — `learningCenter` («Учебный центр», без рейтинга). Курс выбирается рядом с картой в меню выбора героя (`run.selectedCourse`, команда `chooseCourse`) и хранится в забеге (`learning.course`); `courseOf(s)` берёт курс из состояния забега.
- Курс сам задаёт обёртку: названия трёх лабиринтов (`rooms`), босса зала (`boss.unit`, `boss.message`), надпись победы (`victoryTag`) и описание для меню. Это проверяет `validateLearningCourse`. Общий план комнат — `learningRooms` в `data/learning-rules.js`; расписание волн одно, его босс помечен `course: true` и берётся из курса (`bossUnits` в `systems/wave-schedule.js` для бестиария).
- Новый курс — файл в `data` и строка в `data/learning-courses.js`, без новой карты и волн.
- Незаконченные забеги на прежних картах не переносятся: сохранение с картой, которой больше нет, отбрасывается при чтении (`createRunSnapshots`).
